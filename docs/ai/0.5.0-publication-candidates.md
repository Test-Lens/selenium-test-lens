# 0.5.0 publication candidates

!!! warning "Release-candidate preparation, not a release announcement"
    The current publication policy classifies the application/Studio modules and Maven plugin below as intended 0.5.0 artifacts, but the latest released version remains 0.4.0. Maven Central does not yet provide the `0.5.0-SNAPSHOT` goal used by the development guide. Publication classification is necessary release preparation, not evidence that 0.5.0 has shipped.

The current source vertical slice separates deterministic product layers from local orchestration:

| Candidate boundary | Intended consumer role | Current release-preparation status |
|---|---|---|
| `selenium-test-lens-application-model` | Selenium-free, versioned `ApplicationModel` contracts | Classified as an intended 0.5.0 artifact; schema/read compatibility and API gates still decide release readiness. |
| `selenium-test-lens-application-mapper` | Explicit current-page/guided mapping backed by Selector Intelligence | Classified as intended; required selector engine/live dependencies remain explicit. |
| `selenium-test-lens-application-tooling` | Persistence, Page Object generation, drift, context and workflow contracts | Classified as intended; offline API and trusted orchestration boundaries still require release evidence. |
| `selenium-test-lens-test-engineering-studio` | Local loopback UI and launcher | Classified as intended tooling, not a normal runtime dependency. |
| `test-lens-test-engineering-maven-plugin` | Canonical Maven-project launcher with test roots and classpath | Classified as intended; the documented `0.5.0-SNAPSHOT:studio` goal currently requires a local source build. |
| selector engine/live/tooling prerequisites | Existing ranking, live validation, source indexing and correlation | Classified as intended tooling prerequisites; Selector Lab remains nonpublished demo tooling. |

## Required release evidence

Before any candidate becomes a consumer artifact, the release must establish:

- explicit `USER_API`, low-level and internal boundaries in the public API manifest, with correct `@since` data;
- binary/source API gates and clean-room Maven/Gradle consumer compilation for the chosen coordinates;
- dependency isolation: no Selenium in the neutral model, and no JavaParser, browser driver, CLI provider SDK or Studio frontend in normal runtime transitively;
- real Chrome and Firefox mapper contracts, deterministic model and generator tests, generated-source compilation, context-size bounds and security/redaction tests;
- a supported launcher/distribution story for Studio, including project configuration, workspace placement, external agent and WebDriver integration boundaries;
- versioned documentation built from the exact release source and a clear migration/read-compatibility policy for stored models and workflow snapshots;
- release packaging validation updated intentionally, rather than merely removing an artifact from `excludeArtifacts`.
- the publication manifest, Central exclusion list, and every candidate module's effective `maven.deploy.skip` agree.

## Maintainer classification note

`PUBLISHED_TOOLING` means an artifact is intentionally staged and published so the supported tool can run. It does **not** make every public Java type in that artifact stable consumer API. Type-level classification remains authoritative:

- `USER_API` is the documented consumer/bootstrap path;
- `ADVANCED_API` is supported specialized functionality;
- `TOOLING` and `INTERNAL` are published implementation surfaces without a compatibility promise.

For Studio, the intentional consumer surface is the Maven goal plus the explicitly classified bootstrap and browser/agent provider contracts documented in [Getting started](test-engineering-studio-getting-started.md). Package visibility, a generated Javadoc entry, or presence in a published tooling JAR is not by itself an invitation to depend on an implementation class. Release review must compare the API classification manifest and generated catalog with the exact staged artifacts.

The 0.4.0 tag, Maven artifacts and numeric documentation must remain immutable. Development documentation may describe RC preparation, but stable pages must not claim availability until the corresponding artifacts and launch path pass the release gates and are published.
